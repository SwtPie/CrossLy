# CrossLy

Desktop software to help PE teachers organize a school cross-country event: participant registration, race management, live timing, rankings and printable documents (bibs, results).

- Runs fully **offline**: no internet, no user account, no dependency to install.
- Delivered as a **single Windows executable** (double-click to start).
- Single main PC, data stored in a **local SQLite file**.
- **UI language: French** (labels, messages, exported documents). **Code, comments, identifiers, commit messages: English.**

---

## 1. Tech stack

| Layer | Choice |
|---|---|
| Window / shell | **pywebview** (native window embedding the web UI) |
| Backend | Python 3, exposed to the frontend through pywebview's JS API (`window.pywebview.api`) |
| Frontend | HTML / CSS / vanilla JavaScript (no build step, no framework unless decided later) |
| Database | **SQLite** (one `.db` file per installation, or per event export, see section 6) |
| Excel read / write | **openpyxl** |
| PDF generation | **ReportLab** (precise layout for bibs and results) |
| Packaging | **PyInstaller** (one-file `.exe`, Windows only) |

Constraints:
- Everything must work offline: bundle all JS/CSS/fonts locally, no CDN.
- No test framework required: **manual verification** only. Keep logic in small pure functions (import normalization, ranking, VMA percentage) so it stays easy to check by hand.

## 2. Functional documentation

### 2.1 Events
- Independent events (one per date, school or competition).
- Each event has its own participants, races and results.
- Create, edit, delete at any time.
- **Storage**: one SQLite file per event, stored in a `data/` folder **next to the executable**. Participants, races, arrivals and results of an event all live in that same file (see section 3).
- **Backup / transfer**: since an event is a single file, backup = copy the file; import = pick a file. The app also offers export / import buttons that do this.

### 2.2 Participants
- Manual individual add.
- Import from **CSV or Excel (.xlsx)** (`backend/importer.py`, wizard in `frontend/js/screens/participants_import.js`):
  - Downloadable **template** file to fill in (`.xlsx`, generated by the app: headers, sex drop-down, date and VMA formats, a "Mode d'emploi" sheet).
  - Otherwise, flexible **column detection** for arbitrary files: header names are compared without accents, case or punctuation, in French and English (`Nom`, `Last name`, `Né(e) le`, `Date de naissance`, `VMA (km/h)`, `Établissement`, `Division`...). The detected columns are shown and can be changed by hand. The header row is found even under title lines, and the best sheet of a workbook is chosen.
  - A single **"Nom Prénom"** column is supported (capitalized words mark the last name; a checkbox handles "Prénom NOM"; a comma also works).
  - **CSV**: UTF-8 (with or without BOM) or Windows-1252, delimiter `;`, `,` or tab detected. Limits: 10 MB, 5 000 rows. Old `.xls` files are refused with a message asking to save as `.xlsx`.
  - **Preview** before validation (nothing is written until "Importer"): per line a status (to import / to check / duplicate / error) and remarks. The class can be corrected line by line in the preview.
  - **Duplicate detection** on **last name + first name** (accent and case insensitive), against the event and inside the file; duplicates are skipped (the first occurrence in the file is kept).
  - **Name normalization**: names that are entirely uppercase (or lowercase) become `Dupont`, `Jean-Pierre`, `D'Artagnan`; names with mixed case are left untouched. Classes go through the same normalization as manual entry.
  - **Establishment** and **class** fields applied to the whole list: they fill only the lines where the file has no value (a value found in the file always wins).
  - Participants **without VMA** are imported as-is (VMA stays empty, nothing is inferred).
  - Unreadable values (sex, birth date, age, VMA) are **not** blocking: the value is left empty and the line is marked "to check". Missing name or first name, or a name over 80 characters, makes the line an error (skipped).
  - The import is **all or nothing** (one transaction). Bibs are never imported: they are assigned afterwards.
- Bib numbers: automatic assignment in one click, or manual.
  - **Automatic**: only participants without a bib are numbered, in order of establishment, then class, then last name / first name (no establishment last). Numbering starts at a chosen number (default 1) and skips numbers already in use. An option renumbers everyone from scratch (with a confirmation, since bibs may already be printed). A separate action clears all bibs.
  - **Manual**: typed in the participant form; a bib is unique within the event and the app names the participant who already has it.
- Fields and validation (manual add / edit): last name and first name required; sex `M` / `F` (shown as Garçon / Fille) or empty; class normalized to `6X` when it matches the pattern, kept as typed otherwise; establishment free text; birth date (ISO, not in the future) and/or plain age (3-99); VMA 5-30 km/h (comma or dot); bib 1-99999. Two participants cannot share the same last name + first name (accent and case insensitive).
- Real-time search and filtering (client side, accent and case insensitive): free text over name, first name, class, establishment and bib; filters on sex, class, establishment and bib status; sortable columns.

### 2.3 Races
- Unlimited number of races per event.
- A race is defined mainly by its **distance**. The VMA range is **informative only** (it does not restrict who can be registered).
- Registration is unlimited (a participant may be added to several races).
- **Quick add** by combined filters: sex, VMA, class, establishment.
- Individual add with search.

### 2.4 Live timing
- Built-in stopwatch: start, pause, resume, finish.
- One-click **arrival recording** (timestamped), with undo in case of mistake.
- **Bib entry is decoupled from time recording**: arrivals are recorded first as an ordered list of times; bibs are filled in afterwards.
- Bib entry flow: for each finishing position, type the bib number; the app finds the matching participant and shows their name for confirmation. The list is ordered by arrival and is completed in that order.
- **Persistence**: start time and every recorded arrival are written to the database immediately, so a crash, closed window or power cut loses nothing.
- Optional later phase: connect a second device to a local server to enter bibs of the first finishers during the race (see roadmap, phase 9).

### 2.5 Rankings and results
- Automatic ranking with time, real speed (km/h) and **% of VMA**.
  - `speed = distance_km / time_h`
  - `vma_percent = speed / vma * 100`
- Podium view for the top 3.
- **Filtered rankings** by condition: sex, establishment, class and age category (combinable).
- Special statuses: **DNF** (did not finish), **DNS** (did not start), **DSQ** (disqualified). They are listed after the ranked finishers and have no rank.
- **No ties**: positions come from the arrival order, every finisher has a unique rank.
- Post-race correction: add, delete or edit arrivals at any time; rankings update instantly.
- Hide finished races from the main view.

### 2.6 Statistics
Auto-generated charts:
- Participants by sex.
- Participants by establishment.
- Participants by VMA bracket: **0.5 km/h wide brackets**, arithmetic rounding to the nearest 0.5.

### 2.7 Printing and PDF export (high priority)
- **Bibs (dossards)**: PDF export for later printing, selectable **by establishment** and **by class** (one PDF for the whole selection, or one PDF per establishment / per class), with **customization before printing**:
  - fields shown (bib number, last name, first name, class, establishment, race, etc.)
  - bib size
  - logo (image upload)
  - number of bibs per page
- **Results**: PDF export of rankings (general or filtered), also customizable.
- Other exports (start lists, Excel/CSV results) are nice-to-have, see roadmap.

## 3. Data model

One SQLite file per event, so there is no `event` table and no `event_id` column: the file *is* the event. Schema versions are tracked with `PRAGMA user_version` and defined in `backend/migrations.py` (append a new migration, never edit a released one).

- `meta(key, value)`: event `name`, `date` (ISO), `location`.
- `participant(id, last_name, first_name, last_name_key, first_name_key, sex, class, establishment, birth_date, age, vma, bib, created_at)`
  - `*_key` columns hold the normalized (casefolded, accent-free) names; unique on `(last_name_key, first_name_key)` for duplicate detection.
  - `bib` unique, NULL until assigned. `vma` NULL when unknown. `sex` is `M`, `F` or NULL.
- `race(id, name, distance_m, vma_min, vma_max, hidden, timer_status, started_at_ms, paused_at_ms, paused_total_ms, created_at)`
  - `timer_status`: `idle | running | paused | finished`. Timestamps are wall-clock epoch milliseconds, persisted so the stopwatch survives a crash.
- `race_entry(id, race_id, participant_id, status)`: status `registered | finished | DNS | DNF | DSQ`; unique per `(race_id, participant_id)`.
- `arrival(id, race_id, position, elapsed_ms, participant_id)`
  - `participant_id` is NULL until the bib is entered; unique per `(race_id, position)`, and a participant can finish only once per race.
  - Deleting a participant keeps the arrival (time and position) and sets `participant_id` back to NULL.

## 4. Conventions

- Python: PEP 8, type hints where useful, one module per domain (`events`, `participants`, `importer`, `races`, `timing`, `rankings`, `stats`, `exports`).
- Frontend: plain ES modules, one file per screen; no global mutable state outside a small store module.
- All DB access goes through the Python backend; the frontend never touches SQLite directly.
- Every destructive action (delete event, delete race, clear results) needs a confirmation.
- French UI strings centralized in one place to ease later changes.
- Keep it simple: no framework, no dependency that complicates the PyInstaller build.

Suggested layout:

```
crossly/
  CLAUDE.md
  main.py              # pywebview entry point, JS API
  backend/             # domain modules + db.py + migrations.py (the import template is generated by importer.py)
  frontend/            # index.html, css/, js/, assets/
  build/               # PyInstaller spec (phase 9)
```

## 5. Roadmap (deliverable phases)

Each phase ends with something usable and manually verified.

**Phase 0 - Foundations** (done, validated)
App skeleton: pywebview window, Python backend bridge, SQLite schema + migrations, navigation shell, local-assets-only frontend. PyInstaller packaging is **not** a priority here: it is deferred to phase 9. Keep the code packaging-friendly anyway (no data files read from the source tree except through `backend/paths.py`, migrations stored as Python strings).

**Phase 1 - Events** (done, validated)
Create / edit / delete events, event selection screen, event export / import (backup and transfer).
Notes: export uses the SQLite backup API (consistent single file, even in WAL mode) through a native save dialog; import validates and migrates the file in a temporary location, then stores it under a fresh file name (so importing the same backup twice creates two events). Renaming an event changes its name, not its file name. Deleting asks for confirmation and removes the file. Messages the backend shows to the user are French and live in `backend/messages.py`.

**Phase 2 - Participants** (done, validated)
Manual add / edit / delete, search and filters, automatic and manual bib assignment.
Notes: class normalization (`backend/normalize.py`) is already in place and will be reused by the import in phase 3. Forms keep the dialog open when the backend rejects an entry (duplicate, bib already taken...), so nothing typed is lost. Deleting a participant removes their registrations but keeps recorded arrival times without a name.

**Phase 3 - Import** (implemented, awaiting validation)
CSV and Excel import, downloadable template, flexible column detection, preview, duplicate detection (last name + first name), name normalization, establishment applied to whole list, no-VMA handling.
Notes: the file chosen through the native dialog is read by the backend and kept in memory for the wizard (the frontend never handles file paths); it is released after the import or when the wizard is cancelled. All value-parsing helpers (`parse_vma`, `parse_birth_date`, `split_full_name`...) are pure functions. Per-line class correction in the preview covers the "class set manually during import" decision.

**Phase 4 - Races**
Race creation (distance, informative VMA range), registration, quick add by combined filters, individual add.

**Phase 5 - Live timing**
Persistent stopwatch (start / pause / resume / finish), one-click arrivals with undo, crash recovery.

**Phase 6 - Bib entry and rankings**
Bib entry by position with participant lookup, DNF / DNS / DSQ handling, ranking with time / speed / % VMA, podium, filtered rankings, post-race corrections, hide finished races.

**Phase 7 - PDF export (bibs and results)**
Bib PDF by class / establishment with pre-print customization; results PDF (general and filtered) with customization.

**Phase 8 - Statistics**
Sex, establishment and VMA-bracket (0.5) charts.

**Phase 9 - Packaging**
Single-file Windows executable, app icon, clean first launch, data folder location, final manual test on a clean PC.

**Phase 10 - Optional: multi-device bib entry**
Local server on the network, second device (phone / tablet / laptop) enters bibs of first finishers during the race, sync with the main PC. Scope and security to be defined before starting.

**Later ideas (not scheduled)**
Excel / CSV export of results, start lists, diplomas, team (establishment) ranking.

## 6. Open questions

Decided:
- PDF engine: ReportLab.
- Data location: `data/` folder next to the executable.
- Bib customization: fields, size, logo, bibs per page; export by establishment and by class.
- Database layout: **one SQLite file per event** (confirmed). Races live inside their event's file. At startup the app lists events by scanning `data/`, reading name and date stored in each file.
- Ranking / quick-add filters: sex, establishment, class, age category.
- Class naming: applies to **all levels** (`6X`, `5X`, `4X`, `3X`): level digit followed by a section character, where `X` is a letter `A-Z` or a digit `1-9` (e.g. `6A`, `63`). Normalize on import (trim, uppercase, remove spaces / separators such as `6 A`, `6e A`, `6eme3`).
- Class fallback on import: if a value does not match the pattern, keep the raw string found in the column detected as "class" (no rejection). The user can also **set the class manually during import** (per row or for the whole list, like the establishment field).
- Age categories: **deferred**. The data model keeps birth date / age so categories can be added later; the age-category filter is implemented once the definition is decided.

Still open:
- Age category definition (names, boundaries, computed from birth year or age at event date). To decide later.
